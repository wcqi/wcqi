第一阶段:基础入门(第 1-6 步)

第 1 步 — 掌握云计算运维概念以及学习计算机基础

1.1 学习目标

  • 理解"运维"在 IT 体系中的角色定位(从被动救火 → 自动化平台建设)
  • 建立云计算(IaaS/PaaS/SaaS)的整体认知框架
  • 补齐计算机底层基础知识

1.2 核心知识点

1.2.1 云计算基础概念

  • 云计算定义:通过网络"云"将巨大的数据计算处理程序分解成无数个小程序,由多台服务器组成的系统处理后返回结果
  • 服务模型:
  • IaaS(Infrastructure as a Service):基础设施即服务,如阿里云 ECS、华为云 CVM、AWS EC2
  • PaaS(Platform as a Service):平台即服务,如 RDS、容器服务、函数计算
  • SaaS(Software as a Service):软件即服务,如钉钉飞书、企业邮箱、Office 365
  • 部署模型:
  • 公有云(阿里云、华为云、AWS、Azure)
  • 私有云(OpenStack、VMware vSphere)
  • 混合云(公有云 + 私有云,通过专线/VPN 打通)
  • 行业云(政务云、金融云、医疗云)
  • 云原生概念:
  • CNCF(Cloud Native Computing Foundation)定义
  • 四大要素:容器化、微服务、DevOps、持续交付
  • 代表技术:Kubernetes、Docker、Istio、Prometheus

1.2.2 运维工程师的职责与方向

  • 传统运维:服务器上架、系统安装、基础监控、故障排查
  • 应用运维 SRE:保障服务 SLA、参与架构设计、容量规划
  • 数据库 DBA:MySQL/PG/Redis/MongoDB 的部署、备份、复制、调优
  • 自动化运维:用 Ansible/SaltStack/Puppet 实现批量管理
  • DevOps 工程师:打通开发与运维,推动 CI/CD、IaC
  • AIOps 工程师:用 AI/ML 解决告警降噪、根因分析、智能运维

1.2.3 计算机基础补齐

  • 计算机硬件组成:CPU、内存、磁盘(HDD/SSD/NVMe)、主板、网卡、RAID 卡
  • 操作系统原理:内核、用户态/内核态、系统调用、进程/线程、虚拟内存
  • 计算机网络体系:OSI 七层模型、TCP/IP 四层模型、常用协议
  • 数据表示:二进制、十六进制、字符编码(ASCII/UTF-8/GBK)

2.2.2 FHS 目录结构

/           根目录
├── /bin    基本命令(ls、cp、cat)
├── /sbin   系统管理命令(ifconfig、reboot)
├── /etc    配置文件
├── /home   普通用户家目录
├── /root   root 用户家目录
├── /var    可变数据(log、mail、www)
│   ├── /var/log      系统日志
│   └── /var/lib      程序运行数据
├── /usr    用户程序
│   ├── /usr/local    本地安装的第三方软件
│   └── /usr/share    共享数据
├── /opt    可选应用
├── /tmp    临时文件(10 天自动清理)
├── /dev    设备文件
├── /proc   虚拟文件系统(进程、内核信息)
├── /sys    虚拟文件系统(硬件信息)
├── /mnt    临时挂载
└── /media  可移动设备挂载

8.3 核心协议详解

8.3.1 TCP 三次握手

客户端          服务端
  |  -- SYN --->  |    (1.请求连接)
  |  <-- SYN+ACK- |    (2.同意连接)
  |  -- ACK --->  |    (3.确认连接)

8.3.2 TCP 四次挥手

  |  -- FIN --->  |    (1.客户端发完)
  |  <-- ACK ---- |    (2.服务端确认)
  |  <-- FIN ---- |    (3.服务端也发完)
  |  -- ACK --->  |    (4.客户端最终确认)

8.3.3 UDP vs TCP

  • UDP:无连接、快、不可靠(DNS、视频、游戏)

20.3 常用规则

# 允许 lo 回环
iptables -A INPUT -i lo -j ACCEPT

# 允许已建立连接
iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

# 允许 SSH

# DNAT(端口映射)

第 26 步 — 掌握 LVS、keepalived 的内容

26.1 LVS(Linux Virtual Server)

26.1.1 概述

  • 章文嵩博士创立,内核级负载均衡
  • 性能极高,百万级并发
  • 与 Nginx(应用层)互补,常组合使用

26.1.2 三种工作模式

模式 原理 特点
NAT 请求/响应都过 LVS 简单,瓶颈在 LVS
DR(直接路由,默认) 请求过 LVS,响应从 RS 直回客户端 性能最高,同网段
TUN(IP 隧道) 请求过 LVS,RS 通过隧道返回 跨网段

26.1.3 8 种调度算法

  • 轮询(RR)、加权轮询(WRR)
  • 最少连接(LC)、加权最少连接(WLC)
  • IP 哈希(SH)、URL 哈希(LBLC)
  • 目标地址哈希(DH)
  • 最少队列调度(SED)、最少期望延迟(NQ)

            steps {
                git branch: 'main', credentialsId: 'git-creds',
                    url: 'https://gitlab.example.com/dev/myapp.git'
            }
        }

        stage('Test') {
            steps {
                sh 'mvn clean test'
            }
        }

            steps {
                sh 'mvn -DskipTests package'
            }
        }

        stage('Build Image') {
            steps {
                sh """
                    docker build -t ${DOCKER_REGISTRY}/${APP_NAME}:${BUILD_NUMBER} .
                    docker push ${DOCKER_REGISTRY}/${APP_NAME}:${BUILD_NUMBER}
                """
            }
        }

        stage('Deploy') {
            steps {
                sh """
                    kubectl set image deployment/${APP_NAME} \
                      ${APP_NAME}=${DOCKER_REGISTRY}/${APP_NAME}:${BUILD_NUMBER}
                """
            }
        }
    }

        failure { mail to: 'dev@example.com', subject: 'Build failed', body: '...' }

        },
        'timestamp': int(time.time()),
    }

from prometheus_client import Counter, Histogram, generate_latest

app = FastAPI()
REQ_COUNT = Counter('http_requests_total', 'Total HTTP requests', ['method','path','status'])
REQ_LATENCY = Histogram('http_request_duration_seconds', 'Request latency', ['path'])

@app.middleware("http")
async def metrics_middleware(request, call_next):
    start = time.time()
    response = await call_next(request)
    REQ_COUNT.labels(request.method, request.url.path, response.status_code).inc()
    REQ_LATENCY.labels(request.url.path).observe(time.time() - start)
    return response

    return generate_latest()

    return {"status": "ok"}

第 41 步 — 了解 SRE 工程理念

41.1 SRE 起源

  • Google 提出(Site Reliability Engineering)
  • 本质:用软件工程方法解决运维问题
  • 核心理念:自动化 > 文档 > 人工

41.2 核心理念

41.2.1 SLI / SLO / SLA

  • SLI(Service Level Indicator):服务的量化指标
  • 可用性:成功请求 / 总请求
  • 延迟:P99 < 200ms
  • 吞吐:QPS
  • SLO(Service Level Objective):内部目标
  • 可用性 ≥ 99.95%
  • P99 延迟 ≤ 200ms
  • SLA(Service Level Agreement):对外合同
  • 一般比 SLO 宽松,如 ≥ 99.9%

41.2.2 错误预算(Error Budget)

  • 错误预算 = 1 - SLO
  • 例:SLO 99.95%,月错误预算 = 21.9 分钟
  • 用完则冻结发布,投入可靠性建设

41.2.3 消除琐事(Toil)

  • 琐事定义:手动的、重复的、可自动化的、战术性的、突然中断的工作
  • Google 标准:50% 时间不能做琐事
  • 应对:写脚本、平台化、Self-Service

41.3 SRE 实践

41.3.1 事故响应

  • On-Call:7×24 轮值
  • 事故分级:P0(全停)→ P3(小问题)
  • 事故复盘(Incident Review / Postmortem):
  • 时间线
  • 根因(不止 5 Whys,也要找系统性原因)
  • 行动项 + 负责人 + Deadline
  • Blameless:不指责人

41.3.2 容量规划

  • 业务增长预估
  • 压测(如 P99)
  • 资源配比:平时 70%,峰值留 buffer
  • 提前扩容

41.3.3 Chaos Engineering(混沌工程)

  • 主动注入故障,验证系统韧性
  • 工具:Chaos Monkey(Netflix)、ChaosBlade(阿里)、Litmus
  • 原则:在生产环境小范围实验,自动停止

41.3.4 渐进式发布

  • 金丝雀发布(1% → 5% → 25% → 100%)
  • 蓝绿发布(新旧两套切换)
  • 灰度发布(按用户/地域)

41.3.5 可观测性(Observability)

  • 三大支柱:Metrics + Logs + Traces
  • 平台:Prometheus + Loki + Tempo + Grafana
  • 高阶:eBPF(内核级)、OpenTelemetry(统一标准)

41.4 SRE 与 DevOps 的区别

  • DevOps:文化 + 流程(打破开发/运维墙)
  • SRE:DevOps 的一种工程实践(SLI/SLO/Error Budget 等具体方法)
  • AIOps:用 AI 增强 SRE

41.5 推荐学习

  • 《SRE: Google 运维解密》( Betsy Beyer 等)
  • 《Google SRE 工作手册》( Laura Nolan 等)
  • 《SRE生存指南》( John O'Rourke)

41.6 实践任务

  • 做一次事故复盘练习
  • 用 chaosblade 注入一次故障,观察系统表现

第 42 步 — 了解 AI 大模型知识,融入工作中(原图误写为"低42步")

42.1 大模型基础

  • 大语言模型(LLM):参数规模十亿到万亿级
  • 代表:GPT-4/4o、Claude、Gemini、文心、通义、Kimi、DeepSeek、Qwen、GLM
  • 能力:理解、生成、推理、规划、代码
  • 限制:幻觉、知识截止、不能实时联网(默认)、长上下文衰减

42.2 核心概念

  • Token:模型处理的最小单位(中英 1 token ≈ 1-2 字)
  • Prompt:提示词,输入给模型的文本
  • Context:上下文长度(4k/8k/32k/128k/200k)
  • Temperature:温度,控制创造性(0-2)
  • Top-p / Top-k:采样策略
  • Embedding:把文本转为向量,用于检索
  • RAG(Retrieval Augmented Generation):检索增强生成
  • Fine-tuning:微调,让模型适配特定领域
  • Agent:能调用工具、自主完成任务的 AI

42.3 提示词工程(Prompt Engineering)

42.3.1 基本原则

  1. 明确角色:你是 10 年经验的 Linux 运维工程师
  2. 明确任务:给我一个 nginx 限流配置
  3. 明确约束:CentOS 7、nginx 1.20,200 行以内
  4. 明确输出格式:Markdown 代码块 + 注释
  5. 提供示例(Few-Shot)
  6. 链式思考:让我们一步步思考

42.3.2 运维常用 Prompt 模板

你是一位资深 SRE 工程师。请帮我分析以下 Prometheus 告警:

告警名称:{{ alert_name }}
触发时间:{{ timestamp }}
影响范围:{{ service }}
指标值:{{ value }}
请给出:
1. 可能的根因(列出 3 个,按概率排序)
2. 立即处置步骤(命令级)
3. 长期预防建议

42.5 AI Agent 与运维自动化

42.5.1 Agent 能力

42.5.2 运维 Agent 场景
